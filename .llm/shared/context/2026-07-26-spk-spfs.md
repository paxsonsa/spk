# Repo Context Guide: spk — SPFS subsystem

## TL;DR

- SPFS (**S**oftware **P**latform **F**ile**S**ystem) is the storage and runtime-isolation layer that lives under `crates/spfs*` in the `spk` monorepo. SPK (the package manager) is a consumer of it, not the other way around.
- Its job: capture the exact contents of `/spfs`, address that content by hash, store it in local/remote repositories, and re-present it as a per-process-tree filesystem view. Think "git for a filesystem tree" plus "a very thin container runtime."
- Data model is a content-addressed DAG of four persisted object kinds: **Platform → Layer → Manifest → (Tree) → Blob**. All are SHA-256 addressed and serialized as flatbuffers (with a legacy bespoke binary format still readable).
- Storage is behind a `Repository` supertrait with five backends: local filesystem, gRPC/http remote, tar archive, proxy (primary + secondaries), and fallback. Any of them are addressable by URL, e.g. `file:/path`, `grpc://host:port`, `tar:/x.tar`, `proxy:?primary=a&secondary[0]=b`.
- The runtime is assembled by a cluster of small privileged binaries — `spfs` (main CLI), `spfs-enter`, `spfs-render`, `spfs-monitor`, `spfs-fuse`, `spfs-join`, `spfs-clean`, `spfs-winfsp` — coordinating via mount namespaces, overlayfs, and/or FUSE.
- Four mount backends exist (`MountBackend`): `OverlayFsWithRenders` (Linux default), `OverlayFsWithFuse`, `FuseOnly`, `WinFsp` (Windows default).
- Two "escape hatch" features layer on top of the base model: **annotations** (arbitrary key/value data stored in layers, retrievable inside a runtime) and **live layers** (bind mounts of host paths into `/spfs`, declared in a YAML spec file).
- The Rust library API is the crate `spfs`; its top-level verbs are exposed as builder-style structs: `Committer`, `Syncer`, `Checker`, `Cleaner`, plus free functions for runtime lifecycle in `status.rs`.

## How to use (user)

### The mental model

`spfs shell <ref>` / `spfs run <ref> -- cmd` create a **runtime**: a new mount namespace where `/spfs` is composed from the layers named by `<ref>`. Changes made under `/spfs` are discarded when the process exits unless you `spfs commit` them or created the runtime with `--keep-runtime`.

A `<ref>` is an **EnvSpec**: a `+`-separated list of digests, tags, tag-with-history (`tag~1`), or paths to live-layer/spec YAML files. `-` or the empty string means "empty environment". See `crates/spfs/src/tracking/env.rs`.

### Core workflow

```bash
# empty, editable environment
spfs shell -
echo "hello, world" > /spfs/message.txt
spfs info                       # shows "Active Changes: + /message.txt"
spfs commit layer --tag my-layer
exit

# use it
spfs run my-layer -- ls /spfs
spfs shell my-layer --edit      # writable on top of my-layer
spfs commit platform --tag my-platform   # commits the whole stack, not just the diff

# share
spfs push my-platform           # to the 'origin' remote
spfs pull my-platform
```

### Durable runtimes

By default a runtime and its edits vanish on exit. `--keep-runtime` (env: `SPFS_KEEP_RUNTIME`) makes it durable, storing the overlayfs upper dir under `<storage.root>/durable_edits/<name>/upper`:

```bash
spfs run --keep-runtime --runtime-name my-work my-layer -- bash
spfs run --rerun my-work -- bash          # restores layers AND uncommitted edits
spfs runtime list
spfs runtime info my-work
spfs runtime rm my-work
spfs runtime prune ...
```

`--force` with `--rerun` resets the owner/monitor/namespace fields on a runtime left in a bad state.

### Annotations

Arbitrary key/value data attached to a runtime as a layer, readable from inside:

```bash
spfs run --annotation job=1234 --annotation '{shot: abc, seq: 010}' my-layer -- bash
spfs run --annotation-file meta.yaml my-layer -- bash    # '-' reads stdin
# inside the runtime:
spfs info --get job
spfs info --get-all
spfs runtime info --get-all
```

Values longer than `filesystem.annotation_size_limit` are spilled to a separate blob and referenced by digest. Annotations require the flatbuffers encoding format — `spfs run --annotation` errors out if `storage.encoding_format = "Legacy"`.

## Architecture overview

### Layer cake

```
spfs (high-level verbs: commit, sync, clean, check, runtime lifecycle)
  ├── storage  (Repository backends: fs, rpc, tar, proxy, fallback)
  └── tracking (real filesystem <-> Manifest, tags, env specs)
        └── graph (the content-addressed DAG)
              └── spfs-encoding (sha256 + base32 digests)
```

### The object graph

Four kinds are persisted as `Object`s (`ObjectKind`: `Blob`, `Manifest`, `Layer`, `Platform`; `Tree` and `Mask` exist as kinds but are never stored as standalone objects — trees live inside a manifest):

- **Platform** — an ordered stack of layer digests, bottom-up.
- **Layer** — optionally one manifest digest, plus a (possibly empty) list of annotations. A layer with only annotations and no manifest is legal, and that's how `--annotation` works.
- **Manifest** — a complete filesystem tree, stored as a flat list of `Tree`s.
- **Tree** — one directory: entries with `kind`, `object` digest, `mode`, `size`, `name`.
- **Blob** — `{size, payload_digest}`. **A blob's digest is its payload digest** — the code leans on this in several places to skip a hash step (`graph/object.rs`, `Digestible for FlatObject`).

### Encoding and digests

Every stored object is `--SPFS--\n` + 8 header bytes + body. The header carries a `DigestStrategy` and an `EncodingFormat`, both of which have a Legacy and a modern variant:

- `EncodingFormat::Legacy` (bespoke binary) vs `FlatBuffers` (default).
- `DigestStrategy::Legacy` (hash of the legacy encoding, known collision issues) vs `WithKindAndSalt` (default; prefixes a fixed salt + the object kind byte before hashing).

Both are readable forever; only *new* object creation is governed by `storage.digest_strategy` / `storage.encoding_format` in config. The header is preserved on round-trip so an object's digest never changes silently. This is the key backward-compatibility mechanism — don't "helpfully" normalize headers.

### Storage

`Repository` is a supertrait blanket-implemented over `Address + TagStorage + PayloadStorage + ManifestStorage + BlobStorage + LayerStorage + PlatformStorage + graph::Database + graph::DatabaseView`. Implementations dispatch through `RepositoryHandle`.

Backends (`crates/spfs/src/storage/`):

| Scheme | Type | Notes |
| --- | --- | --- |
| `file:` / none | `fs::MaybeOpenFsRepository` / `OpenFsRepository` | On-disk: `objects/`, `payloads/`, `tags/`, `renders/<user>/`, `durable_edits/`, plus a `VERSION` file for migrations. Supports lazy open and `?create=true` |
| `grpc:` / `http2:` | `rpc::RpcRepository` | Talks to `spfs server`; object/tag traffic over gRPC, payload bytes over plain http |
| `tar:` | `tar::TarRepository` | Unpacks to a temp fs repo, repacks on drop. Mainly for spk package archives |
| `proxy:` | `proxy::ProxyRepository` | Reads fall through to secondaries for objects/tags missing from the primary. Pure read-through — **nothing is copied back**. `include_secondary_tags` controls tag visibility |
| `fallback:` | `fallback::FallbackProxy` | Same shape, but secondaries are used specifically to **repair** payloads and blobs missing from the primary during rendering, copying them into the primary |
| *(wrapper)* | `pinned::*` | Any repo pinned to a point in time via `?when=`; tags become read-only |

Two orthogonal wrappers apply to any remote: `?when=<timespec>` (pin tag view to the past) and `?tag_namespace=<path>` (segregate tags). Tag namespace must be set *before* pinning — see `RemoteConfig::open`.

Only fs repositories support **renders** (`RenderStore`) and **durable runtime paths** (`Storage::durable_path` returns `Error::DoesNotSupportDurableRuntimePath` otherwise).

### Runtime

A `Runtime` = `Data { name, author, status, config }` persisted in the *local repo* as two tags:

- `spfs/runtimes/meta/<name>` → a blob holding the JSON-serialized `Data`
- `spfs/runtimes/data/<name>` → a `Platform` object holding the layer stack

Runtime tags deliberately bypass the configured tag namespace (`runtime::Storage::new` clears it) so `spfs runtime list` sees every runtime on the host.

`Status` carries the layer `Stack`, `editable`, `running`, `owner` pid, `monitor` pid, and the `command`. `Config` carries the overlayfs `upper_dir`/`lower_dir`/`work_dir`, startup script paths, `mount_namespace`, `mount_backend`, `secondary_repositories`, `durable`, and `live_layers`.

`OwnedRuntime` is the ownership marker: `upgrade_as_owner` (the entry process) and `upgrade_as_monitor` (the watchdog) each claim a runtime exactly once.

### Mount backends

| Backend | How `/spfs` is produced | Localization required? |
| --- | --- | --- |
| `OverlayFsWithRenders` | Each layer rendered to a directory (hard-linked from `payloads/`), stacked as overlayfs lowerdirs | **Yes** — everything must be synced local first |
| `OverlayFsWithFuse` | FUSE mount serves as the single lowerdir; overlayfs upperdir for edits | No (read-through) |
| `FuseOnly` | FUSE mounted directly at `/spfs`; read-only | No |
| `WinFsp` | Windows filesystem protocol provider | No |

`MountBackend::requires_localization()` is the switch that decides whether `spfs run` syncs the whole environment down before launching.

### Process choreography (Linux, overlayfs backend)

```
spfs run <ref>
  ├─ resolves <ref> to digests, syncs from origin into the local repo
  ├─ creates + saves a Runtime
  └─ exec spfs-enter --runtime-name ...
       ├─ enters a new mount namespace (RuntimeConfigurator::enter_mount_namespace)
       ├─ becomes root (capabilities), removes mount propagation
       ├─ mounts tmpfs at the runtime dir, spawns spfs-render for layer renders
       ├─ mounts overlayfs at /spfs, masks deleted entries
       ├─ spawns spfs-monitor (which upgrades itself as the runtime's monitor)
       ├─ [if fuse] spawns spfs-fuse
       ├─ drops back to the original user
       └─ execs the shell (with startup scripts) or the target command
spfs-monitor
  └─ when the last process in the tree exits → spfs-enter --exit → unmount, then delete the runtime
     (unless durable, in which case the metadata and upper dir are kept)
```

`RuntimeConfigurator` in `env.rs` is a typestate: `RuntimeConfigurator<NoUserChanges, NoMountNamespace>` → `enter_mount_namespace()` → `become_root()` → mount operations → `become_original_user()`. The type parameters make it a compile error to call a privileged mount helper without having escalated first. Worth preserving if you touch that file.

### Startup scripts

Shell selection and startup are in `bootstrap.rs` + `runtime/startup_{sh,csh,ps}.rs`. On entry, the startup script sources everything matching `*.sh` / `*.csh` in `/spfs/etc/spfs/startup.d`, alphabetically, then hands off to the user's shell or the target command. `environment.variable_names_to_preserve` captures listed env vars before `spfs-enter` and restores them from inside the startup script (needed for `TMPDIR`, `LD_LIBRARY_PATH`, which are otherwise cleared).

## Key components (deep links)

### `graph` — the DAG

- **Purpose**: define, encode, digest, and traverse the object graph.
- **Main types**: `Object`/`FlatObject<T>`, `Platform`, `Layer`, `Manifest`, `Tree`, `Blob`, `Annotation`, `Stack`, `ObjectKind`, `Header`, `DigestStrategy`, `EncodingFormat`.
- **Traits**: `Database` (write/remove), `DatabaseView` (read/iter/walk/find), `DatabaseExt`, `HasKind`/`Kind`.
- **Invariants**: blob digest == payload digest; headers are preserved verbatim across read/write; `FlatObject` holds a pre-validated flatbuffer + an offset, so the `unsafe` constructors demand a genuinely valid buffer.
- **Refs**: `crates/spfs/src/graph/object.rs`, `graph/stack.rs`, `crates/spfs-proto/schema/spfs.fbs`.

### `tracking` — the real-filesystem side

- **Purpose**: turn directories into `Manifest`s and back, name things, diff things.
- **Main types**: `Manifest`/`ManifestBuilder`/`ManifestNode`, `Entry`/`EntryKind`, `Diff`/`DiffMode`, `Tag`/`TagSpec`, `EnvSpec`/`EnvSpecItem`/`SpecFile`, `TimeSpec`, `BlobRead`.
- **Note**: `tracking::Manifest` is the *mutable, tree-shaped, generic-over-user-data* form; `graph::Manifest` is the *immutable, flat, persisted* form. `to_tracking_manifest()` / `create_layer_from_manifest()` convert. Confusing the two is the most common newcomer mistake here.
- **Refs**: `crates/spfs/src/tracking/manifest.rs`, `tracking/env.rs`, `tracking/tag.rs`.

### `storage` — persistence

- **Purpose**: one interface, many backends.
- **Entry points**: `spfs::open_repository(url)`, `Config::get_remote(name)`, `Config::get_local_repository()`, `config::open_repository_from_string` (tries name, then URL, then bare path).
- **Invariants**: `PayloadStorage::write_data` is `unsafe` — writing a payload without also writing the `Blob` that tracks it leaves an orphan. Use `RepositoryExt::commit_blob`.
- **Refs**: `crates/spfs/src/storage/repository.rs`, `storage/fs/repository.rs`, `storage/proxy/`, `storage/rpc/`.

### `runtime` — session state

- **Purpose**: define and persist runtimes; manage durable upper dirs and live layers.
- **Main types**: `Runtime`, `OwnedRuntime`, `Data`, `Status`, `Config`, `MountBackend`, `Storage`, `LiveLayer`/`BindMount`, `SpecApiVersion`.
- **Invariants**: exactly one owner and one monitor per runtime; durable upper-dir names must be unique across runtimes on a host (`check_upper_path_in_existing_runtimes`); durable paths must be on local disk, not NFS, or the overlayfs mount fails.
- **Refs**: `crates/spfs/src/runtime/storage.rs`, `runtime/live_layer.rs`, `runtime/overlayfs.rs`.

All follow the same builder shape: construct with a repo, chain `with_*`, then call an async verb. All take a pluggable reporter for progress/UI.

The `unsafe` markers on `reinitialize_runtime` / `change_to_durable_runtime` are about `std::env::set_var` in a possibly-threaded process, not memory safety.

### Network API (feature `server`)

`spfs server` exposes three gRPC services plus a plain-http payload channel:

- `Repository` — just `Ping`.
- `DatabaseService` — `HasObject`, `ReadObject`, `FindDigests` (stream), `IterObjects` (stream), `WalkObjects` (stream), `WriteObject`, `RemoveObject`, `RemoveObjectIfOlderThan`.
- `TagService` — `LsTags`, `ResolveTag`, `FindTags`, `IterTagSpecs`, `ReadTag`, `InsertTag`, `RemoveTagStream`, `RemoveTag`. Every request carries a `namespace` field.
- `PayloadService` — `IterDigests`, `HasPayload`, `WritePayload`, `OpenPayload`, `RemovePayload`. Note `WritePayload`/`OpenPayload` return **URLs**, not bytes; the actual transfer happens over http against those URLs. This is deliberate — gRPC message limits would otherwise cap file size.

`spfs-vfs` has its own tiny service (`crates/spfs-vfs/src/proto/defs/vfs.proto`): `VfsService.Mount(root_pid, env_spec)` and `VfsService.Shutdown()`, used to drive a running `spfs-fuse` process.

Schemas live in `crates/spfs/src/proto/defs/*.proto`; conversions to/from the Rust types are in `crates/spfs/src/proto/conversions.rs`.

## Configuration & environments

Config files, in increasing precedence (`config::load_config`):

1. `/etc/spfs.conf` (ini, legacy)
2. `/etc/spfs.{toml,yaml,json,ini}`
3. `~/.config/spfs/spfs.conf` (ini, legacy)
4. `~/.config/spfs/spfs.{toml,yaml,json,ini}`
5. `SPFS_*` environment variables (double underscore separates nesting: `SPFS_STORAGE__TAG_NAMESPACE`; single-underscore forms still work for backwards compatibility and take precedence)

Sections: `[storage]`, `[remote.<name>]`, `[filesystem]` (+ `[filesystem.overlayfs_options]`), `[fuse]`, `[monitor]`, `[user]`, `[sentry]`, `[environment]`.

Defaults worth knowing:

- `storage.root` → `dirs::data_local_dir()/spfs` (i.e. `~/.local/share/spfs` on Linux), falling back to `/tmp/spfs`.
- `filesystem.backend` → `OverlayFsWithRenders` on Unix, `WinFsp` on Windows.
- `filesystem.secondary_repositories` → `["origin"]`.
- `storage.digest_strategy` / `encoding_format` → `WithKindAndSalt` / `FlatBuffers`. Note the *fallback* when no config can be loaded at all is `Legacy` for both, deliberately conservative (`HeaderBuilder::new`).
- `fuse.enable_heartbeat` → `false` in code; the docs example shows `true`.

Environment variables used directly by the code (beyond `SPFS_*` config overrides):

| Variable | Meaning |
| --- | --- |
| `SPFS_RUNTIME` | Name of the active runtime; how `active_runtime()` finds itself |
| `SPFS_KEEP_RUNTIME` | Default for `spfs run --keep-runtime` |
| `SPFS_FILESYSTEM_TMPFS_SIZE` | Size of the runtime tmpfs mount |
| `SPFS_LOG_FILE`, `SPFS_LOG_TIMESTAMP` | Logging |
| `SPFS_SUPPRESS_OVERLAYFS_PARAMS_WARNING` | Set by the Makefile during tests |
| `SPFS_METRICS_SYNC_TIME_SECS` | Injected into the runtime by `spfs run` |
| `CI_PIPELINE_ID` | With the `gitlab-ci-local-repo-isolation` feature, isolates the local repo per pipeline |

**Secrets**: there is no credential handling in spfs. Remote repositories are unauthenticated — access control is expected to come from filesystem permissions or network placement. The only secret-adjacent config is `sentry.dsn`.

**Privileges**: `spfs-enter` (and `spfs-clean --remove-durable`) need elevated capabilities to create namespaces and mount overlayfs. RPM packaging installs them with capabilities attached; a from-source install needs the equivalent setup or the runtime commands will fail.

## Testing & quality

- **Unit tests** are colocated as `*_test.rs` files pulled in with `#[cfg(test)] #[path = "./x_test.rs"] mod x_test;`. That's the convention throughout — a new module `foo.rs` gets `foo_test.rs` beside it, not a `tests/` file.
- **Fixtures**: `crates/spfs/src/fixtures.rs` (rstest fixtures for tmp repos, etc.), `crates/spk-storage/src/fixtures.rs` for the spk side.
- **Integration tests**: `crates/spfs/tests/integration/` — shell scripts split into `privileged/` and `unprivileged/`, driven by `run_tests.sh` / `run_privileged_tests.sh` / `test_harness.sh`. These are the ones that actually exercise mounting.
- **Benchmarks**: `crates/spfs/benches/spfs_bench.rs` (criterion).
- **CI**: `.github/workflows/rust.yml` (build/test/lint), `coverage.yml` (grcov, needs `spfs run`), `rpm.yml`, `cspell.yml`, plus docs link-checking. `make act` runs the workflows locally via nektos/act with `--privileged`.
- Testing anything that mounts requires privileges; `make test` sidesteps some of this by running the suite inside an spfs runtime.

## Extension points & customization

- **New storage backend**: implement the component traits (`Address`, `TagStorage`, `PayloadStorage`, `BlobStorage`, `LayerStorage`, `ManifestStorage`, `PlatformStorage`, `graph::Database`, `graph::DatabaseView`) — `Repository` then blanket-implements. Add a variant to `RepositoryHandle`, a variant to `RepositoryConfig`, and a scheme arm in `RemoteConfig::from_address`.
- **New CLI subcommand**: either add a variant to `Command` in `crates/spfs-cli/main/src/bin.rs` with a `cmd_*.rs` module, or ship a standalone `spfs-<name>` binary — the `External` clap subcommand resolves those through `which_spfs()` and beside the current exe, so no registration is needed.
- **Progress/UI**: every long-running verb takes a reporter trait (`CommitReporter`, `SyncReporters`, `CheckReporter`, `CleanReporter`, `ComputeManifestReporter`, render reporters). Silent, tracing, and console implementations already exist; add your own rather than threading `indicatif` through the logic.
- **Blob hashing**: `Committer::with_blob_hasher` swaps the `BlobHasher` (`InMemoryBlobHasher` vs `WriteToRepositoryBlobHasher`).
- **Path filtering**: `Committer::with_path_filter` for partial commits.
- **Runtime startup**: drop files into `/spfs/etc/spfs/startup.d/*.sh|*.csh`. Keep them tiny — they run on every environment entry.
- **Live layers**: a YAML spec (`api: v0/layer`, `contents: [{ bind_mount: { src, dest } }]`) referenced in an EnvSpec, letting host paths appear inside `/spfs` without being committed. See `runtime/live_layer.rs`; ordering matters (a directory mount can shadow a later file mount, and spfs errors rather than silently losing it).
- **Schema evolution**: `crates/spfs-proto/schema/spfs.fbs` — flatbuffers rules apply, only append fields to tables, never modify structs. The repo also has ast-grep rules under `crates/spfs-proto/ast-grep/rules` guarding proto usage.

## Operational notes

- **Deployment**: RPMs are published per release (`make rpms`, `rpmbuild.Dockerfile`). Binaries must be installed with the right capabilities for `spfs-enter`. A shared `origin` repository is typically an NFS-mounted fs repo or an `spfs server` behind gRPC.
- **Bootstrapping an fs remote**: the directory structure has to exist. `mkdir -p /path/to/spfs-storage/{objects,payloads,tags}` (or use `?create=true` in the address).
- **Observability**: `tracing` throughout, with `-v` levels mapping to filters; optional syslog for background processes; optional Sentry (`configure_sentry` in `spfs-cli-common`, plus the `sentry-miette` crate for error reporting integration). `spfs-fuse` and `spfs-monitor` exchange a heartbeat so an orphaned FUSE mount shuts itself down (`Fuse::HEARTBEAT_FILENAME_PREFIX`, `fuse.heartbeat_*` config).
- **Performance hotspots**:
  - Rendering layers for overlayfs — hard-linking thousands of files. Tuned by `--max-concurrent-blobs` / `--max-concurrent-branches` on render, and the `renders/<user>/` proxy dir for dedup.
  - Sync — `--max-concurrent-manifests` / `--max-concurrent-payloads`.
  - Manifest computation on commit — `DEFAULT_MAX_CONCURRENT_BLOBS` / `DEFAULT_MAX_CONCURRENT_BRANCHES`.
  - The flatbuffers encoding exists specifically to avoid decode cost — `FlatObject` reads fields directly out of the byte buffer, and there's a thread-local `FlatBufferBuilder` in `graph/mod.rs` to avoid allocation churn.
- **Cleanup**: `spfs clean` (via `spfs-clean`) prunes tags then GCs unreferenced objects. Because tags root the GC, syncing *tags* (rather than digests) into a local repo pins objects and defeats cleaning. `spfs run` deliberately resolves tags to digests before syncing for exactly this reason (see `cmd_run.rs`, `with_tag_items_resolved_to_digest_items`).

### Q&A anchors

- *"Where does `/spfs` actually get mounted?"* → `crates/spfs/src/env.rs` (`mount_env_overlayfs`, `mount_env_fuse`, `mount_runtime`), called from `status_unix.rs`.
- *"How is a digest computed?"* → `impl Digestible for FlatObject` in `graph/object.rs`; blobs short-circuit to the payload digest.
- *"Where do runtimes live on disk?"* → they don't, directly: metadata is a blob tagged `spfs/runtimes/meta/<name>` in the local repo. Durable upper dirs live at `<storage.root>/durable_edits/<name>/`.
- *"How do I add a remote?"* → `[remote.<name>]` in config, either `address = "<url>"` or `scheme = "..."` + fields.
- *"Why did my `spfs run` sync so much?"* → `MountBackend::requires_localization()` is true for `OverlayFsWithRenders`.
- *"How does spk use spfs?"* → `crates/spk-exec/src/exec.rs`: resolves a solution to layer digests, sets `rt.status.stack`, calls `spfs::remount_runtime`.

### Glossary

| Term | Meaning |
| --- | --- |
| **Digest** | SHA-256 content hash, rendered as base32 in text |
| **Blob** | File contents (the object); **payload** is the actual bytes on disk |
| **Manifest** | A whole filesystem tree, content-addressed |
| **Layer** | A manifest and/or a set of annotations; the unit users tag |
| **Platform** | An ordered stack of layers |
| **Stack** | The ordered list of layer digests in a runtime or platform, indexed bottom-up |
| **Tag / TagSpec** | Human name → digest, with history; `name~1` means "one version back" |
| **Tag namespace** | A prefix segregating tags within one repository |
| **EnvSpec** | `+`-separated list of refs describing an environment |
| **Runtime** | An active (or durable) spfs session: a stack + mount config + process state |
| **Durable runtime** | A runtime whose metadata and edits survive process exit |
| **Render** | An on-disk materialization of a manifest, hard-linked from payloads, for overlayfs |
| **Live layer** | Host paths bind-mounted into `/spfs` without being committed |
| **Annotation** | Arbitrary key/value data stored in a layer, readable inside the runtime |
| **Localization** | Syncing all required data into the local repo before running |
| **Masking** | Marking a file deleted relative to a lower layer (`ObjectKind::Mask`) |

## Doc/code discrepancies found

Live code is truth; these are places `docs/` has drifted:

1. `docs/spfs/develop/runtime.md` says `spfs-enter` "calls back into the `spfs init-runtime` command." **No such command exists.** There is no `init-runtime` anywhere in the tree. `spfs-enter` now builds and execs the shell directly via `spfs::build_shell_initialized_command` / `build_interactive_shell_command` (`crates/spfs-cli/cmd-enter/src/cmd_enter.rs`). `spfs init` is unrelated — it creates an empty repository.
2. `docs/spfs/develop/design.md` says spfs "provides two implementations of the storage api, a local filesystem store and a tar archive store." There are **five**: fs, rpc (gRPC), tar, proxy, fallback — plus the `pinned` wrapper.
3. `docs/spfs/develop/runtime.md` refers to a `ManifestViewer` trait for renders. The current code uses `LocalRepository::render_store()` and the `renderer` module in `storage/fs/`; no `ManifestViewer` trait exists.
4. `docs/admin/config.md` shows `fuse.enable_heartbeat = true`; the code default is `false` (`Fuse::default()` in `config.rs`).
5. The design doc's object-graph diagram omits annotations entirely, which is a significant part of the current `Layer` shape.

## Open questions

- **WinFSP maturity.** `docs/admin/install.md` calls Windows "experimental… can be mounted and viewed, but not modified." How much of `crates/spfs-vfs/src/winfsp/` is exercised by CI? Check: `.github/workflows/rust.yml` for a Windows job, and whether any test targets `winfsp-backend`.
- **`fallback` is undocumented.** `docs/admin/config.md` documents the `proxy` scheme but not `fallback`, even though both are configurable remotes. Worth documenting the repair-vs-read-through distinction for users.
- **Migration story is currently vestigial.** `MIGRATIONS` in `crates/spfs/src/storage/fs/migrations/mod.rs` is an **empty vec**, so `migrate_repo` iterates nothing and `spfs migrate` amounts to a canonicalize + rename dance. The machinery is there for a future format break; there is nothing to migrate today. `docs/spfs/develop/migrations.md` (13 lines) does not say this.
- **`use_mount_syscalls`.** Config docs say it "may be removed in the future and behave as if set to true," default `false`. Check `env.rs` for how far along that transition is.
- **Server auth.** `grep -rin "auth|token|tls" crates/spfs/src/server/` returns nothing, so there is no authentication or transport security in the server implementation itself. Before relying on that for a deployment, confirm whether anything is expected to terminate TLS in front of it — nothing in this repo does.
